# 开发计划：认证能力与下一阶段

更新日期：2026-11-17（Asia/Shanghai）

当前基线：**0.1.0**。本文承接 [后续任务](NEXT_TASKS.md)，聚焦“需要登录认证的 MCP 服务”和下一阶段的产品优先级，不替代具体任务的验收清单。

## 结论

- 本地服务、以及用静态 Header / API Key 的远程服务，使用链路已经基本闭环：导入 → 添加 → 测试 → 保存 → 后台验证 → 启停 / 重启 / 删除。
- 真正未闭环的是 **OAuth 类远程 MCP**。它不完全是插件层的问题，当前 DSH MCP 客户端没有提供 OAuth 授权 seam。
- 认证要分层推进：**先做现在能做的 Token / API Key + 认证状态；OAuth 先做技术决策，不直接开写本地代理。**
- 除认证外，最值得补的是：真实桌面验收与 E2E、失败诊断、项目作用域、版本更新、备份来源分离。工具级权限和 Tool Search 仍应等待官方接口。

## 当前状态

### 已经闭环的部分

- 多来源导入、批量 JSON、逐行测试、一次 revision 写入、失败零写入、撤销本批。
- 表单 / JSON 独立草稿；重名提示与改名；手动来源持久化与删除。
- 官方 MCP Registry 搜索、详情、预填添加；不静默安装。
- 配置导出（可选密钥）、备份恢复、环境变量与请求头引用。
- 中英双语跟随 DSH locale。
- 单元测试 99 项、构建和语法检查通过。

### 没有闭环的部分

- 尚未在用户日常桌面 profile 完成系统性的整页验收。
- 没有可重复的桌面端到端测试和 CI。
- OAuth 服务没有完整授权、刷新、过期、撤销和重新授权流程。
- 没有认证状态模型，也没有 `needs-auth` 识别。
- 失败诊断只有最后错误和工具列表，缺少启动日志、阶段和历史。
- 项目级发现只覆盖启动目录，不能切换作用域。
- 不能比较已安装版本与 Registry 版本，也不能升级 / 固定版本。
- 备份恢复没有把来源信息和连接配置分离，冲突预览不足。

## 认证能力

### 当前约束

当前依赖 `@deepseek-ai/dsh-mcp-client@0.2.2-rc.3`。其 `streamable-http` 配置只有 `headers`，没有 OAuth 字段：

- 没有 Protected Resource Metadata / Authorization Server Metadata 发现。
- 没有动态客户端注册（DCR）。
- 没有 PKCE 授权、token 刷新、撤销。
- 没有 401 后自动重新授权。
- 插件拿不到 `mcpManager` 的连接生命周期，不能替它刷新 token。

因此“完整 OAuth”不能只在 `dsh-mcp-hub` 内实现。`NEXT_TASKS.md` 也已把完整 OAuth 列为等待官方 `needs-auth` / 授权 seam 的事项。

### 认证分层

| 类型 | 现在能否做 | 方案 |
| --- | --- | --- |
| API Key / Bearer Token | 能，优先做 | 粘贴或导入 token → 存 DSH 凭证 → Header 使用 `${credential:...}` → 复用测试 / 保存 |
| OAuth 2.1 远程 MCP | 只能做半套 | 浏览器授权拿 token 可以；自动刷新与 401 重试需要 DSH core 或本地代理 |
| 云厂商签名（AWS SigV4、GCP ADC） | 不能直接做 | 需要代理或上游支持 |
| stdio 本地服务 | 已支持 | env / 本机已有登录态；本质仍是 API Key 或本机凭证 |
| 从其他应用导入的 OAuth 登录态 | 不能迁移 | 明确提示重新授权，不假定复制配置等于复制登录 |

### 三条路线

- **A. 推动 / 等待 DSH core 支持**：最干净。插件只负责授权 UI、状态和凭证生命周期。
- **B. 插件内置本地反向代理**：插件持有 token、刷新、注入 Header，MCP 配置指向 `127.0.0.1`。可做，但要处理流式转发、session、超时、端口安全和代理生命周期，成本和风险都高。
- **C. Token 助手（过渡）**：浏览器授权或手动粘贴 token，存凭证，写静态 Bearer Header。能用，但 token 过期后需要重新授权，不是完整 OAuth。

**建议：先做 C；A 作为正式方向；B 只在出现明确必须 OAuth 的服务时做技术验证。**

### 凭证与安全原则

- token 存 DSH 凭证服务，不写普通配置，不出现在导出、日志和错误详情中。
- Header 模板使用 `${credential:...}`；不要在前端保存明文 token。
- 认证状态至少区分：`unauthenticated`、`authorizing`、`authenticated`、`expired`、`error`。
- 从其他应用导入的配置不携带 OAuth 登录态；首次使用必须重新授权。
- 目录只是目录，不代表安全审核；远程服务仍要展示地址、发布者、认证要求和风险提示。

## 分阶段计划

不绑定发布日期，按三个迭代推进。

### 迭代 1：把现有闭环做可信，补 Token 认证

目标：真实桌面环境可重复验收；需要 API Key / Token 的远程服务可以安全添加。

- 真实 DSH desktop profile 验收：stdio、Streamable HTTP、凭证引用、启停 / 重启 / 删除、重启恢复。
- 把人工验收转为可重复 E2E，接入 CI。
- 补齐保存边界：停用配置、缺失引用、超时阶段、失败诊断。
- 认证探测：401 / 403 记为 `needs-auth`，UI 显示“需要认证”，不当作普通连接失败。
- Token 助手：
  - 粘贴 API Key / Token；
  - 存入 DSH 凭证，不写普通配置；
  - Header 使用 `${credential:...}`；
  - 测试连接、保存、显示认证状态；
  - 提供“重新授权 / 清除凭证”。
- 明确提示：从其他应用导入的配置不会携带 OAuth 登录态。

验收：

- 一个需要 Bearer Token 的远程服务，能在不出现明文密钥的情况下完成添加、测试、保存。
- token 失效时提示重新授权，而不是只报连接失败。
- 导出、日志、错误详情中不出现 token 明文。

### 迭代 2：OAuth 决策与实现

先做技术决策，不直接开写：

- 查清目标 DSH 版本的 `needs-auth` / 授权 seam 是否可用。
- 如果可用：插件只做授权 UI、状态、凭证生命周期。
- 如果不可用：评估本地代理方案，做 2–3 天技术验证，覆盖 Streamable HTTP 流式转发、session、刷新、端口安全。
- 如果两条都不可行：明确说明当前版本只支持 Token，OAuth 服务需手动提供 token。

OAuth 完整实现应覆盖：授权、刷新、过期、撤销、重新授权、账号 / 作用域展示、401 自动重试。

验收：

- 授权失败、用户取消、token 过期、刷新失败都有明确状态。
- 不把 refresh token 暴露给浏览器或导出文件。
- 不对其他应用导入的登录态做静默迁移。

### 迭代 3：管理深度

- 项目作用域与配置归属。
- 诊断日志、stderr、健康检查、自动重连。
- 已安装版本 vs Registry 版本、升级 / 固定版本。
- 备份恢复：来源信息分离、冲突预览。
- 搜索筛选：远程 / 本地、认证类型、包类型、更新时间。
- 安全提示：目录未审核、命令预览、第三方代码警告。

### 后续阶段

- 单工具权限 / 审批（等官方接口）。
- Tool Search（等 DSH 能控制最终工具 Schema）。
- 私有 / 企业目录。
- 团队共享、配置同步。

## 风险与不做

- 不在插件内实现隐藏的 OAuth 本地代理，除非完成流式转发和安全验证。
- 不把 token 写入普通配置、前端状态或导出文件。
- 不把官方 Registry 当作安全审核或安装背书。
- 不在没有官方权限 seam 的情况下伪造单工具开关。
- 不为了“看起来支持 OAuth”而静默降级成静态 token。

## 下一步

1. 完成真实桌面 profile 验收，记录实际 DSH 版本、平台和问题。
2. 实现 401 探测和 Token 助手，先把非 OAuth 的认证服务跑顺。
3. 确认目标 DSH 版本的 OAuth seam；如果不存在，再决定是否做本地代理验证。
4. 按迭代 1 的验收清单补 E2E 与 CI。
