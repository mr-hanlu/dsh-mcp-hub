# 桌面实例验收清单

面向 **真实 DSH 桌面应用**的人工验收：这些项要么依赖真实渲染（深浅色、窄窗口），要么依赖真实宿主生命周期（重启、凭证服务）与桌面注入的主题变量。

2026-11-19 起，Host 层的重启恢复（`test:e2e` 阶段 3）、无凭证服务时的保存/读取拒绝、官方 Manager 行边界已有自动化；第二轮又补了删除后重新导入、外部配置变更、并发保存、验证中关闭与卸载（阶段 4/5），以及 tarball 安装（`npm run test:tarball`）。下面保留人工项是为了复核**桌面界面**，不再需要从零手工验证逻辑。

自动化已经覆盖的部分见 [开发进度](DEVELOPMENT_PROGRESS.md#已验证范围与边界)；这里只列还需要人看、人点、人判断的项。

**2026-11-19 结果：维护者已在桌面实例人工复核第 1–3、5–6 组（主题 / 窄窗、凭证缺失文案、官方 Manager 边界、删除清理），均通过。** 第 4 组是「凭证服务未挂载」的开发辅助场景，未要求桌面自助验证；此后移除批量导入的撤销横幅属于纯页面改动，由 `test:ui` 回归。P0-1 据此标完成。

## 前置

- 目标版本：DSH `0.2.2-rc.5`（macOS 已按 rc.3 验收过；rc.5 上自动化基线全绿）；记录实际版本，与本文不符时先按实际版本重试。
- 安装方式：README「安装」方式 A（插件页 → 添加插件 → 本仓库绝对路径，link 安装），profile `desktop`。
- 每次验收前确认：`npm test && npm run check && npm run build` 为绿，`lib/` 是刚构建的产物。
- 记录用统一表头（见文末模板）。**不通过的项不要勾选**，直接在表里写现象。

打开页面：设置 → MCP Hub。

## 1. 样式、深浅色与窄窗口

先跑一遍 `npm run test:layout`：它会在临时 profile 里截浅色 / 深色 / 700px 窄窗口 / 窄窗口编辑窗口四张图（`tests/e2e/artifacts/layout-*.png`），并断言没有横向溢出、编辑窗口不超出视口。**这一步覆盖的是插件自带的回退配色与布局**，已经自动化，不需要人工重复。

桌面里仍要人工确认的是 **DSH 主题变量**那条路径：Web 构建不注入 `--dsw-alias-*`，只有桌面应用会提供，插件会优先用它们而不是回退配色。

| # | 操作 | 预期 |
| --- | --- | --- |
| 1.1 | DSH 切到浅色主题，看「已添加 / 本地导入 / 在线搜索」三个页签与服务列表 | 文字、边框、徽标都跟随 **DSH 主题变量**；没有白底黑字或对比度过低的元素（与 `layout-light.png` 对照，颜色应更贴合应用本身而不是插件的回退色） |
| 1.2 | 切到深色主题，重复 1.1 | 同上；隐藏值、诊断里的红色告警仍清晰可读 |
| 1.3 | 打开「添加 MCP」，在 JSON / 表单间来回切换 | 两个页签的草稿都在；页签上的未保存小圆点跟随状态 |
| 1.4 | 把窗口拖到最窄（约 720px 以下），看列表行、服务详情、编辑窗口 | 不出现横向滚动条；长 URL、长参数在容器内换行或截断，按钮不重叠 |
| 1.5 | 在窄窗口下打开环境变量行 | 名称 / 值 / 图标操作三项不挤压，图标仍可点中 |

## 2. 重启 DSH 后恢复

`test:e2e` 阶段 3 已在 Host 层断言：重启后条目重新连接、工具重新注册、失败结论与原因文本不变、手动导入来源仍在。下面只看桌面界面是否把这些状态如实画出来。


| # | 操作 | 预期 |
| --- | --- | --- |
| 2.1 | 添加一个本地服务（如 `npx` 或本机命令），确认已连接并注册工具 | 行状态「已连接」、工具数正确 |
| 2.2 | 完全退出 DSH，重新打开，进入 MCP Hub | 列表仍是同一个服务；来源记录（「DSH 配置」或导入来源）还在 |
| 2.3 | 故意制造一次失败：把该服务的命令改成一个不存在的路径后保存 | 保存后自动停用，行内显示失败原因；**记录这条原因** |
| 2.4 | 再重启一次，重新打开 MCP Hub，展开该服务的「诊断」 | 「最近一次验证」仍是上次的失败原因，不是空的或「已验证通过」 |
| 2.5 | 把命令改回正确值并启用 | 恢复「已连接」，旧失败结论被新结论替换 |

## 3. 凭证缺失与凭证相关提示

| # | 操作 | 预期 |
| --- | --- | --- |
| 3.1 | 添加一个带明文 API Key 的服务，保存 | 提示「密钥已写入 DSH 凭证」；配置里只留 `${credential:MCPHUB_…}`（详情 → 配置 可核对） |
| 3.2 | 在 DSH 凭证管理里删掉该凭证（或改名），回到 MCP Hub 看该行 | 状态变为「缺少凭证」或失败，诊断里能看出是凭证问题；不显示明文 |
| 3.3 | 重新填回凭证（凭证管理里新建同名值），不重启 DSH | 服务自动重连（客户端监听凭证引用更新），行状态回到「已连接」 |
| 3.4 | 打开该服务的编辑窗口，点「显示密钥」 | 10 秒内显示真实值且可复制，到时自动收回；同时只有一行处于显示状态 |

## 4. 需要开发辅助的场景（凭证服务未挂载）

宿主没有挂载 `credentials` 服务时保存应当**失败并说明原因**，而不是把明文写进配置。该行为已有单测锁定（保存与 `reveal` 都返回 `CREDENTIAL_UNAVAILABLE`，且零写入）；下面只在需要核对界面文案时做，人工造这个环境要改 profile，不建议自助操作：

- 由维护者用一个临时 profile 起一个不注入 `credentials` 的宿主，再走一次保存；
- 预期：保存返回失败，错误文案指出凭证服务不可用，配置未被写入；
- 结果记录在本文末尾表格，附临时 profile 的构造方式。

## 5. 与官方 Manager 已有服务 / 插件注册 / 继承配置的边界

| # | 操作 | 预期 |
| --- | --- | --- |
| 5.1 | 在 DSH 官方 MCP 管理界面里已有服务时打开 MCP Hub | 列表能读到官方条目，来源标注与实际一致（DSH 配置 / 插件注册 / 继承配置） |
| 5.2 | 对「插件注册」的行点编辑 / 删除 / 启用开关 | 三个操作都不可用（按钮禁用或开关 disabled）；诊断里能说明它由插件提供 |
| 5.3 | 对「继承配置」的行点编辑 / 改名 / 删除 | 编辑与删除被拒绝并说明「只能停用」；启用开关可点 |
| 5.4 | 停用一个继承配置行，再到官方界面确认 | 官方状态随之变化，没有出现第二份同名服务 |
| 5.5 | 在官方界面里改一个服务的配置，回到 MCP Hub | 行内配置跟着更新；没有重复行，也没有把官方改动覆盖回去 |

## 6. 删除与清理（可选，桌面上再看一次）

| # | 操作 | 预期 |
| --- | --- | --- |
| 6.1 | 删除一个正在运行的服务 | 行消失；若短暂出现「已删除，清理中」也能在几秒内消失 |
